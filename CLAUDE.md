# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A static web app (`index.html`) that extracts article text from a URL and reads it aloud, plus an optional Cloudflare Worker (`worker/`) that proxies premium text-to-speech. The page is deployed as-is to GitHub Pages — no build step, no dependencies, no tests. All HTML, CSS, and JS live inline in `index.html`.

It's an installable PWA: `manifest.webmanifest` registers an Android share target (shared links arrive as GET params — usually in `text`, not `url` — handled by `handleSharedUrl()` in `index.html`), and `sw.js` is a minimal network-first service worker required for installability. A share navigation has no user gesture, so both engines treat blocked autoplay (`not-allowed` / `NotAllowedError`) as "paused, tap play" rather than an error. Icons live in `icons/` (root `/*.png` is gitignored; `icons/` is not).

## Running and testing

Open `index.html` directly in a browser, or serve the directory (e.g. `python3 -m http.server`) and reload after changes. Deploying the page is just uploading `index.html` (and `README.md`) to a repo root with GitHub Pages serving from the `main` branch root.

Design docs for past features live in `docs/superpowers/specs/` (dated markdown, e.g. the Cloudflare voice tiers and the background-playback/smart-prev design) — read the relevant one before reworking those areas. Root-level `*.png` screenshots and `.playwright-mcp/` are gitignored QA artifacts; `icons/` is tracked.

Note both READMEs lag the code: `README.md` describes only the free `speechSynthesis` path (no premium Worker, PWA, or share target), and `worker/README.md` predates Aura-2 and the multi-origin `ALLOWED_ORIGINS`. Trust `index.html` / `worker/worker.js` over them.

The Worker is deployed separately with wrangler from `worker/` (`npx wrangler deploy`); see `worker/README.md`. Its shared access key is a Worker secret (`wrangler secret put ACCESS_KEY`) — never commit it. The page finds the Worker via the `CF_WORKER_URL` constant in `index.html`.

## Architecture

**Article extraction** — `loadArticle()` fetches `https://r.jina.ai/<article-url>` (Jina Reader, keyless) with headers that request plain text (`X-Return-Format: text`), drop images, and strip page chrome via `X-Remove-Selector` (structural landmarks, boilerplate class names, and article furniture like `figcaption`/`.byline`/`.tags` — deliberately not `<table>` or `<time>`). The text then passes through a cleanup pipeline: `cleanArticle()` (strips residual Jina preamble/markdown, adds terminal punctuation so the voice pauses) → `normalizeForSpeech()` (removes leaked CSS, reference markers `[12]`, nav remnants) → `expandForSpeech()` (expands `$`, `%`, `e.g.`, ranges, etc. into spoken words; strips emoji). This pipeline was tuned against ~11 real sources — be conservative when changing regexes; each one guards against a specific false positive noted in its comment. Extraction failure falls back to a manual paste textarea.

**Line structure is load-bearing** — `cleanArticle()` joins blocks with `\n` (not spaces) and `readText()` collapses spaces per line rather than all whitespace, because Jina's text mode puts each block on its own line and everything below reads that structure.

**Boilerplate trimming** — `stripBoilerplate(lines, title)`, gated on the "Trim article extras" checkbox (`trimExtras`, default on, persisted as `trim` in `ar_prefs` with no `PREFS_VERSION` gate). Called from both `cleanArticle()` and `readText()`, so pasted text is trimmed too; it's idempotent because a trimmed article starts with prose, which leaves no head zone. Deliberately rule-based, not an LLM call: the signal is a line's shape and position, so it stays offline, keyless, instant and debuggable (every drop is logged via `console.debug`). Every pattern is case-insensitive and anchored to a whole line, because Jina's text mode puts each block on its own line — "Share" alone is a button, "Share prices fell…" is prose.

Four passes, in this order (the order is load-bearing):
1. **Tail cut** (`cutTail()`), first, because the marker is often junk in its own right — drop "Most read" as a label and the anchor for the cut is gone. Cuts from the first `TAIL_CUT_RE` marker in the last 60 lines (related lists, tags, copyright, closing byline+bio, paywall pitches, a bare `Jul 29` date heading a "more stories" list), or from a `STRONG_TAIL_RE` marker anywhere (`References`, `External links` — no article prose is a line reading just "References"). Three guards: a length cap (≤160 chars — labels, not paragraphs), a character check (≥60% of the text must sit above the cut, 40% for strong markers), and `proseFollows()` — whatever comes after must not read like body prose.
2. **Junk lines**, anywhere: `JUNK_EXACT_RE` (ads, read-time, player/consent/caption chrome, pagination, Wikipedia hatnotes, membership pitch bullets), `JUNK_SHORT_RE` (patterns starting with innocent words — only trusted on lines ≤48 chars with no terminal punctuation, and with no trailing `\b` since real pages glue labels together as "SubscribeSign In"), `CREDIT_RE` (photo/wire credits — the line must *end* in the agency, so "…, Reuters reported." survives), `CITATION_RE` (bibliographic references: DOI/ISBN/`Retrieved 3 May 2024`/`Author (2024). "Title"`), cookie-consent paragraphs (two independent signals *and* within the first 25 lines, so an article about tracking survives), and an author-box bio.
3. **Nav runs**: four or more consecutive `isLabelLine()` lines. This is the single biggest source of junk in real dumps — a BBC page arrives with ~100 nav labels — and runs are what separate nav from a real heading, which always sits alone between paragraphs. The label definition is looser for the first 15 lines (promo grids run longer than nav labels) and the whole pass is skipped if such runs are >50% of the text, which means a link roundup where the "nav" is the content.
4. **Head zone** (up to the first prose line, capped at 8 lines), located *after* the passes above — real pages open with consent paragraphs and nav blobs long enough to look like the first body paragraph. `headScore()` ≥ 3 over `HEAD_RE` (datelines, `By Jane Doe`, bylines glued to a role or timestamp, section kickers) plus shape features (short, unpunctuated, carries a year, ALL CAPS, name-shaped per `NAME_STOPWORDS`, one- or two-word kicker, follows another dropped line) minus sentence-ish signals. Also drops a headline that duplicates `articleTitle`, which is why `loadArticle()` resolves the title *before* cleaning.

Tuned against ten live dumps (BBC, Guardian, Ars Technica, The Verge, TechCrunch, NPR, Smashing, dev.to, freeCodeCamp, Wikipedia); typical result is 15–25% off a news page and ~50% off a Wikipedia article (the reference list), with no body prose dropped in any of them. Note `X-Return-Format: text` means Jina returns **no `Title:` line**, so `articleTitle` is normally the URL slug and the title-dedupe rule rarely fires. Known residue: Smashing's newsletter/course promo block above the article, and NPR's membership pitch on very short pages (too small for the tail cut's character guard).

Toggling the checkbox re-cleans the loaded article in place from `rawArticle` (the retained extraction) and resumes at the proportional character position.

**Two TTS engines**, selected by the "Use premium voice" checkbox (`activeEngine()`):

- **Browser** — `speechSynthesis`. Chunks of ~400 chars (`CHUNK_SIZE`, shared by both engines) play sequentially via `utterance.onend` chaining in `speakChunks()`. Rate changes require re-speaking the current chunk (the API can't change rate mid-utterance). Word-level highlighting uses `onboundary` where supported; voices that never fire it (Android Chrome network voices, iOS Safari) fall back after a 1.5s grace to time-estimated sentence highlighting (`startSpeechTick`). Voices load asynchronously — `loadVoices()` is wired to both initial load and `onvoiceschanged`, and filters to curated en-US/en-GB voices.
- **Cloudflare (premium)** — `playCloudflareChunk()` POSTs each chunk to the Worker and plays the returned MP3 through **two alternating `<audio>` elements** (`cfPlayers`, with `cfAudio()` returning the active one and `cfActive` its index). Both are created once, appended to the document, and only ever re-`src`ed — never replaced with `new Audio()`, and `stopAll()` resets them (`removeAttribute("src")` + `load()`) instead of discarding them — so the user's first-tap activation carries forward to every later chunk. Double-buffering is the other half of screen-off playback: `prepareNextCfChunk()` fetches and `load()`s chunk N+1 into the idle element *while* N plays, so `advanceCfChunk()` (running from `onended`) swaps `cfActive` and calls `play()` **synchronously, awaiting nothing** — an `await` there lets the platform suspend the page in the silent gap, which is what used to kill playback mid-article. `cfPrepared` records which chunk is buffered; when it doesn't match, the handoff falls back to the fetch-then-play path. `navigator.audioSession.type = "playback"` is set where supported (iOS), and `visibilitychange` resumes premium audio the platform paused while backgrounded. Has an in-memory audio cache with next-chunk prefetch, and supports live `playbackRate` changes. Highlights the current sentence (`buildSentenceSpans` + a `timeupdate` listener) — estimated from audio time, since there are no word-boundary events. On quota/capacity errors (the Worker returns 429 + a `detail` string) `quotaFallback()` degrades tiers automatically — Aura-2 → Aura-1 → MeloTTS → free browser voice — re-chunking by character position so the listening spot survives the engine switch.

**Stale-callback guards** — both engines replay/skip by cancelling and restarting, so every async callback validates it still owns playback before acting: browser callbacks check `utterance === currentUtterance`; Cloudflare callbacks capture and compare the incrementing `cfPlayToken`. `stopAll()` invalidates both. When touching playback, preserve this pattern or prev/next will double-advance chunks.

**Screen wake lock** — `syncWakeLock()` (called from every `setControls()` and on `visibilitychange`) holds a `navigator.wakeLock` "screen" lock **only** while the browser engine is playing, because `speechSynthesis` is suspended by the platform when the screen locks and no web API can prevent that. The premium engine takes no lock — real `<audio>` playback is meant to survive a locked screen. Acquisition is async, so the callback re-checks `playbackState`/`activeEngine()` before storing the lock; all failures are swallowed.

**Headings in the reading view** — `chunkArticle()` (not `splitText()` directly) builds the chunks: a line `isHeadingLine()` accepts — short, ≤12 words, no terminal punctuation except `?`/`!`, not a list item — becomes a chunk of its own, recorded as `heading` in the parallel `chunkKinds` array, while prose between headings still fills to `CHUNK_SIZE` as before. `renderChunks()` turns that into `.chunk.heading` styling. A heading owning its chunk is what makes this survive word/sentence highlighting (only `textContent` is rebuilt, the class stays) and is why `cleanArticle()` appends no period to headings — the chunk boundary already makes both engines pause.

**Shared playback state** — module-level `chunks` / `chunkIndex` / `playbackState` (`idle | playing | paused`) drive everything: the clickable chunk reading view (`renderChunks()` / `highlightChunk()`), progress bar + ETA, prev/next/restart controls, keyboard shortcuts (Space/K, arrows), and the Media Session API (lock-screen controls). Speed has ± buttons either side of the slider (`nudgeRate()`, one 0.05 step, clamped to the slider's own min/max); `applyRate()` is the live half (label, `playbackRate` on both players) and `commitRate()` the settled half (persist, and re-speak for the browser engine, which can't change rate mid-utterance).

**Sentence-level navigation** — `sentenceStarts` (per-chunk sentence offsets, same regex as `splitText`) plus `chunkCharOffset` (where playback of the current chunk started) enable sentence prev/next (‹ › buttons, ↑/↓ keys), tap-a-sentence in the reading view (`charOffsetFromPoint`), and tap-to-seek on the progress bar. The browser engine re-speaks the chunk from a sliced offset (highlighting maps relative `charIndex` back through `chunkCharOffset`); the premium engine seeks `cfAudio.currentTime` proportionally, since TTS pace is roughly constant. The section prev button keeps its Spotify-style double-press behavior (`handlePrev`).

**Premium tier defaults** — the `<details class="premium">` section is `open` in the markup; the only thing that collapses it is `quotaFallback()`'s final degradation to the free browser voice (nothing left to configure until the quota resets), and the "needs an access key" paths still force it back open. The markup defaults are premium **on** with **Aura-2**, and the voice select defaults to a **Random** entry (`RANDOM_VOICE`, a client-only sentinel): `resolveCfVoice()` draws a real voice from the active model's list once per reading — not per chunk, so one article keeps one narrator — stores it in `activeCfVoice`, and names the pick in the option's label (`Random (Luna)`). Everything downstream (cache key, Worker request) uses `activeCfVoice`, so the sentinel never leaves the page; re-resolving on model change matters because the Aura-1 and Aura-2 voice lists differ. `preferredCf` holds the tier the user actually chose, separate from what's live. `quotaFallback()` degrades the live model but never persists it, and `loadArticle()` calls `restorePreferredCf()` so every new article starts again at the best tier (the daily quota resets). Only manual changes to the premium controls re-`snapshotCfPrefs()`. `ar_prefs` entries are gated on `PREFS_VERSION` (now 3): older entries keep their browser voice/speed but their premium fields are ignored, since v1 persisted quota degradations and v2 stored the then-default voice explicitly, which would defeat the Random default.

**Persistence (localStorage)** — voice/speed/model prefs (`ar_prefs`), per-URL resume positions + article titles pruned after 7 days (`ar_positions`), and the premium access key (`cf_access_key`, stays client-side; sent only to the Worker). The "recently played" list (`renderRecent()`) is a UI over `ar_positions`: in-progress articles, tap to resume; finishing an article clears its entry.

**The Worker** (`worker/worker.js`, single file) — gates on `X-Access-Key` (timing-safe compare), allowlists models (MeloTTS, Aura-1, Aura-2) and voices, caps text at 2000 chars, pins CORS to the GitHub Pages origin + localhost, and calls Workers AI through the `AI` binding so no Cloudflare API token exists anywhere. The client's voice lists in `index.html` are a curated subset of the Worker's allowlists — keep them in sync when adding voices.
